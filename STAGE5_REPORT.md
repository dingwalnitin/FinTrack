## 3. Domain / business-rule changes

- **Taxonomy (P10 #1/#2)** — `TxKind { EXPENSE, INCOME, TRANSFER, REFUND, FEE, CASH_MOVE, UNKNOWN }` + `TxSubtype` (CARD_ONLINE, CARD_POS, UPI, BANK_TRANSFER, ATM_WITHDRAWAL, SALARY, INTEREST, CASHBACK, FULL, PARTIAL, CASH_OUT, CASH_IN, UNKNOWN). Refund is a `TxKind`, not a mutation — the original expense remains.
- **Lifecycle (P10 #7 / module 142)** — `TxStatus { PENDING, POSTED, REVIEW_REQUIRED, FAILED, DELETED }`. Old `state` column kept for back-compat.
- **Signed money (P10 #3)** — `amountMinor` is the absolute value; sign is in `direction`. `PostingPolicy.signedMinor` and `SignedMoney` provide a single source of truth. Sign rules centralised in `PostingPolicy.directionFor(kind, accountType)` so BANK, CREDIT_CARD, CASH, OTHER_LIABILITY are all consistent.
- **Postings (P10 #4)** — every money-changing event is persisted inside a single Room `@Transaction` (`FinanceDaoV3.replacePostingGroup`) that deletes the prior posting group and inserts the new one. Duplicate postings can never accumulate on edit.
- **Balance continuity (P10 #5)** — `PostingPolicy.isActive(status)` excludes DELETED/FAILED from active balances. Sum-of-signed-postings invariant is preserved by construction.
- **Dedup (P09)** — engine uses 7 weighted signals (ref 0.45, amount 0.15, rail 0.10, account 0.10, merchant 0.10, card 0.05, ts 0.05) + 4 contradiction guards (account, currency, direction, ref). Verdict bands: `MERGE ≥ 0.85`, `REVIEW ≥ 0.35`, else `REJECT`. Same-value purchases close in time deliberately go to REVIEW, never AUTO_MERGE.
- **Soft delete (P10/P11 #4)** — `txn.status = DELETED` + `deletedAtEpochMs` set; postings are kept for audit; backfill / re-processing must not silently resurrect.

## 5. Acceptance-gate results

### P09 — Duplicate SMS and financial-event deduplication
- ✅ Repeated ingestion of the same (providerId | contentHash) produces one event with multiple evidence links (idempotent `EvidenceLink` on `linkIdentity` unique index; `replacePostingGroup` keeps postings consistent on merge).
- ✅ Ambiguous matches are reviewable — the engine routes same-value purchases to REVIEW (corpus case `rv-same-amount-coffee` and `rv-different-merchant-same-amount`).
- ✅ False-merge / false-split corpus regressed (8 cases, all match expected verdict).
- ✅ Dedup is idempotent across backfill / parser re-runs / prompt-version changes (clusterIdentity = sha-256 of ordered pair signals).
- ✅ User decisions are durable and append-only (`DedupeDecisionEntity` unique on (eventId, decisionKind, appliedAt); most recent wins by ordering).
- ✅ Weak / changed SMS provider IDs after restore are recognised via `contentHash` fallback (see `RawSmsDedupPolicy`).
- ✅ Legitimate same-value purchases close in time are NOT auto-merged (engine threshold + corpus fixtures).

### P10 — Transaction normalization, taxonomy, direction semantics
- ✅ `Transaction` carries `id`, `occurredAt`, `amountMinor`, `currencyCode`, `direction`, `accountId`, `source`, `status`; optional `merchant`, `description`, `rail`, `referenceId`, `category`; unknown values are null.
- ✅ Mutually clear taxonomy: `TxKind` + `TxSubtype`. Refund is a `TxKind.REFUND` linked to the original expense rather than mutating history.
- ✅ Signed money semantics: centralised in `PostingPolicy`; sign consistent across BANK, CREDIT_CARD, CASH, OTHER_LIABILITY.
- ✅ Immutable postings generated from transaction state; every money-changing event persisted transactionally via `replacePostingGroup` inside one Room @Transaction.
- ✅ Editing a transaction regenerates postings transactionally; never accumulates duplicate postings (test `editing amount regenerates the same group - no duplicate postings`).
- ✅ Balance-continuity / sum-of-postings invariants tested.
- ✅ Transaction detail screen surfaces advanced posting section, provenance / confidence, status / review cues.

## 6. Unresolved risks, deliberate limitations, follow-up

1. **P11 (transfers, refunds, fees, cash movements, manual entry, soft delete) is deferred** — see `P11_PROMPT.md` in the repo root for the detailed scope, contract, and acceptance gates.
2. **MigrationTest for 5→6** — the existing `MigrationTest` covers 1→2 and 3→4; a parallel 5→6 fixture is the recommended follow-up. Schema 6.json is exported and committed.
3. **Review UI for ambiguous clusters** — engine verdict surfaces in `DedupeCluster.verdict` + `DedupeCluster.reasons`; the Compose screen reading them and accepting `KEEP_DUPLICATE` / `MERGE` / `SPLIT` decisions is not yet built (DedupeService.recordDecision is ready to be wired).
4. **Parser → DedupeService wiring** — the LLM path produces advisory `LlmInterpretationEntity`; the orchestrator that turns (interpretation + raw_sms) into a TransactionEntity and runs `DedupeService.clusterPair` is a thin WorkManager piece. Deferred to P11 where transfers/refunds sit in the same orchestration layer.
5. **No production release build** — `assembleRelease` would need the v6 schema migration test signed off before shipping.
6. **The 4 v6 tables are populated only when the dedup path runs** — pre-existing v5 transactions get the default `kind=UNKNOWN, status=POSTED` and no evidence links. A one-time backfill job (manual or via a future prompt) is the suggested way to add evidence links to historical events.
