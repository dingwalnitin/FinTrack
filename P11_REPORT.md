## 3. Domain / business-rule changes

- **Two-sided transfers (P11 #1)** — `TransferService.linkTransfer` writes two `TransactionEntity` rows (`kind=TRANSFER`, one DEBIT on source, one CREDIT on destination), two `LedgerEntryEntity` rows sharing a posting group, and one `TransferEntity` — all inside one Room `@Transaction` (`FinanceDaoV4.recordTransfer`). Both sides share `transferGroupId`. Income/expense read paths filter `kind != 'TRANSFER'`.
- **Cash movements (P11 #4)** — reuse the transfer pipeline with `cashMovementSubtype = CASH_OUT/CASH_IN`; bank account ↔ cash wallet both reflect the movement; excluded from income/expense metrics.
- **Refunds (P11 #2)** — refunds are separate events referencing the original expense via `RefundLinkEntity`. The original postings are never mutated. Partial refunds carry their amount on the link.
- **Fees (P11 #3)** — fees are explicit `kind=FEE` events linked to their parent charge via `TransactionLinkEntity(role=FEE)`. Never collapsed into the parent amount.
- **Manual entry (P11 #5)** — `messageId=null`, `sourceKind=MANUAL_ENTRY@manual-v1`, `correctionOrigin=null` on create. Edits set `USER_CORRECTION` provenance only when a non-display field changes (amount/account/currency/kind/date). Validation returns `Result.failure` with human-readable messages.
- **Soft delete / restore (P11 #6)** — tombstone keeps postings for audit; restore flips back to POSTED and clears the tombstone (audit `RESTORED`). All read paths exclude `status=DELETED`. Re-processing never resurrects a deleted event — a fresh SMS creates a new event instead.
- **Explicit statuses (module 142)** — parser transitions PENDING→POSTED/REVIEW_REQUIRED/FAILED; user corrections stay POSTED; soft-delete is DELETED.
- **Contradicting SMS (P11 #7)** — new evidence is added as RAW_SECONDARY; significant contradictions flip status to REVIEW_REQUIRED without mutating the original row.

## 5. Acceptance-gate results

- ✅ A transfer creates two transactions, two postings, one `TransferEntity` row, all inside one @Transaction; neither side counts in income/expense aggregates; both sides can be edited and the transfer link survives (stable `transferGroupId`).
- ✅ A refund transaction is a new event with its own postings, linked to the original via `RefundLinkEntity`; original postings unchanged; expense + refund sums equal net economic impact.
- ✅ Every detected fee is its own event; never collapsed into the parent's amount.
- ✅ Cash movements show in both the cash wallet and bank balances; sum of the two sides equals net movement; excluded from income/expense metrics.
- ✅ Manual entry round-trips; validation errors return `Result.failure(...)` with human-readable messages; edits preserve the postings invariant (replace-group semantics).
- ✅ Deleted transactions are invisible to aggregations; postings and evidence preserved for audit; restore is USER-only and audited; backfill never resurrects a deleted event from a fresh SMS.
- ✅ Every detail view shows evidence, history, and linked events; unknown fields stay unknown (empty sections render an honest "none" message, never fabricated data).
- ✅ Contradicting SMS adds evidence without mutating the original; significant contradictions surface REVIEW_REQUIRED.
